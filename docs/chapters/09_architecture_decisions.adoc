= Architecture Decisions

[[adr-treesitter]]
== ADR-1: Use Tree-sitter for Parsing

:grammar-url: https://github.com/seflue/tree-sitter-asciidoc[]

*Status:* Accepted

*Context:*
The LSP server needs a parser that handles incomplete and syntactically invalid documents and produces a concrete syntax tree that preserves all source information (whitespace, comments, positions).
Three parser options were evaluated: writing a custom PEG parser, using an existing AsciiDoc parser library, and using the cathaysia Tree-sitter grammar for AsciiDoc.

*Decision:*
We chose Tree-sitter as the parser.
The grammar is the project's fork ({grammar-url}) of the archived cathaysia grammar, included as the git submodule `vendor/tree-sitter-asciidoc`; the root Cargo.toml patches both grammar crates to it via `[patch.crates-io]`.
The dual-grammar approach (block + inline) aligns with AsciiDoc's own processing model.

*Consequences:*

* Positive: Error recovery and syntax highlighting queries are provided by the Tree-sitter framework with minimal custom code.
* Positive: Grammar fixes are made in the fork and take effect through the submodule pin.
* Negative: The grammar may not cover all AsciiDoc constructs. Gaps are fixed in the fork.
* Negative: The dual-grammar approach adds complexity to the parser integration; for details, see xref:chapters/08_concepts.adoc#parsing-concepts[Parsing Concepts].

[[adr-rust]]
== ADR-2: Implement in Rust

*Status:* Accepted

*Context:*
The LSP server is a long-running process that must handle concurrent document updates from the editor.
Memory safety, performance, and ecosystem support for both Tree-sitter and LSP protocol handling are critical requirements.
TypeScript (via vscode-languageserver), Rust (via tower-lsp-server), and Go (via gopls patterns) were considered.

*Decision:*
We chose Rust as the implementation language.
The `tower-lsp-server` crate provides an async-first LSP framework.
Tree-sitter's Rust bindings are first-class, and Rust's ownership model prevents data races in a long-running server process.

*Consequences:*

* Positive: Memory safety without garbage collection pauses.
* Positive: The Rust ecosystem provides tooling (cargo, clippy, rustfmt) and a strong type system that catches bugs at compile time.
* Negative: Higher learning curve compared to TypeScript. Contributors need Rust experience or must be willing to learn.
* Negative: Longer compile times compared to TypeScript or Go.

For the building block structure, see xref:chapters/05_building_block_view.adoc#building-blocks[Building Block View].

[[adr-semantics]]
== ADR-3: Resolve AsciiDoc Semantics in asciidoc-core

*Status:* Accepted

*Context:*
Asciidoctor converts one top-level document per run.
Includes are textual: `include::` is replaced before parsing, and an attribute entry applies from its line on in that reading order.
So the value of `{x}` in a shared file depends on the top-level document and the position, not on the line alone.
If `book.adoc` and `web.adoc` include the same file and set different `imagesdir` values, both results are correct.
`docdir` is the folder of the converted document, and Asciidoctor locks it.
Tree-sitter parses syntax only. It knows nothing about attribute values, include order or `docdir`.
A second, semantic parser could provide them, but two parsers can disagree on the structure of the same document.

*Decision:*

* There is no second parser. `asciidoc-core` resolves attributes, includes, `docdir` and xref targets on top of the Tree-sitter trees. `asciidoc-lsp` translates the results into LSP types.
* Attribute values are resolved per (top-level document, position). A definition applies from its line on, and an unset hides an earlier value.
* A top-level document is a document that no other document includes.
* `{docdir}` is the folder of the top-level document. A `:docdir:` entry in a document or in `.asciidoctorconfig` is ignored.
* Each top-level document is read as the editor previews it: its `.asciidoctorconfig` chain first, then the document.
* `asciidoc-core` returns the results for all top-level documents and picks none. If they agree, a feature shows one result. If they differ, it shows each with the document name.
* For paths, an included file is also resolved as its own preview, with its config chain and its own folder as base. Hover shows this preview as information. Go to definition, find references, rename and completion follow only the top-level documents that read the file. Attribute values show only the top-level documents.

*Consequences:*

* Positive: Hover, go to definition, completion and path checks share one resolution rule.
* Positive: Several top-level documents on the same files (print and web) work without relying on file names.
* Negative: The top-level document comes from the include graph, not from the build configuration.
