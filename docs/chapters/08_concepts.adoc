= Cross-Cutting Concepts

== Tree-sitter Integration

[[parsing-concepts]]
The server uses the AsciiDoc grammar in two languages: `tree-sitter-asciidoc` for block-level structure and `tree-sitter-asciidoc-inline` for inline markup.

The block grammar is parsed first and identifies sections, attributes, and block macros.
Paragraph text is opaque in the block tree.
The block tree yields the text ranges of paragraphs, and the inline grammar parses each range on its own via `set_included_ranges`.
Parsing all ranges in one call lets markup in one paragraph pair with markup in another and produces false nodes.

The parsers are created in the `parser` module of `asciidoc-core`, and the `extractors` module reads sections, anchors, xrefs, and includes from the trees.

== Parsing on Change

The server uses full-document sync.
Every change re-parses the whole file, and the extracted data of that file is replaced in the workspace.

== Fault Tolerance

Documents in an editor are often incomplete.
Tree-sitter inserts `ERROR` and `MISSING` nodes into the parse tree instead of aborting, so the rest of the document is still analyzed.

== Include Resolution

Include paths can contain attribute references.
The resolver handles these forms:

* Simple relative paths: `include::chapter1.adoc[]`
* Attribute-based paths: `include::{chaptersdir}/chapter1.adoc[]`
* Paths with leveloffset: `include::chapter1.adoc[leveloffset=+1]`
* Non-AsciiDoc includes: `include::config.yaml[]`

Attributes in the path are substituted first, then the path is resolved relative to the directory of the including file.
An include that cannot be resolved is reported as a diagnostic on the directive.
